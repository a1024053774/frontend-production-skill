# 修复计划模板

审查后写可交接的修复计划时读。执行者可能是能力较弱、没有任何上下文、也没有审美判断的模型，所以计划必须包含一切，而且精确。不要写"见上面的审计"或"用我们讨论过的缓动"。改编自 `improve-animations` 的计划模板（MIT），扩展到所有镜头。

````markdown
# NNN — <简短的祈使句标题>

- **状态**：TODO
- **提交**：<写计划时 `git rev-parse --short HEAD` 的输出>
- **级别**：P0 | P1 | P2 | P3（动效审计可另注 HIGH | MEDIUM | LOW）
- **镜头 / 类别**：<例如 工程-状态与数据、动效-缓动与时长>
- **关联问题**：<问题编号>
- **预估范围**：<文件数、大致规模>

## 问题

哪里不对、在哪、为什么影响用户。每个位置写成 `path/to/file.tsx:123`，并原样附上当前代码：

```css
/* src/components/dropdown.css:14 — current */
.dropdown { transition: all 400ms ease-in; }
```

## 目标

精确的最终状态。所有值都写出来（曲线、时长、弹簧参数、媒体查询、接口字段、状态名），不写"换个好点的缓动"：

```css
/* target */
.dropdown {
  transition: transform 200ms var(--ease-out), opacity 200ms var(--ease-out);
  transform-origin: var(--transform-origin);
}
```

## 要遵循的项目约定

这个代码库已经怎么做，附一个执行者应该模仿的范例（token 名、文件位置、属性写法）：

- 缓动 token 在 `src/styles/tokens.css`；新曲线加在那里，例如 `--ease-out: cubic-bezier(0.23, 1, 0.32, 1);`
- <已经做对的 文件:行>

## 步骤

1. <每步一个具体修改：文件、改什么、改完的代码。>
2. …

## 边界

- 不要碰 <范围外的文件或组件>。
- 不要改标记或结构，只改 <本计划涉及的属性>（除非某一步明确要求）。
- 不要加新依赖。
- 某一步和你看到的代码对不上（提交之后代码有变动），停下报告，不要即兴发挥。

## 验证

- **机械检查**：<精确命令，如类型检查、lint、构建、相关测试，以及预期结果>。
- **行为 / 手感检查**：运行界面，触发 <交互>，确认：
  - <可观察的检查，例如"下拉框从触发器缩放出来，而不是从中心">
  - <例如"连点开关，动画从不从零重来">
  - <动效：在 DevTools Animations 面板把播放速度调到 10%，确认 <细节>>
  - <动效：在 Rendering 面板打开 `prefers-reduced-motion`，确认位移去掉了、opacity 反馈还在>
  - <手机端：在真机上确认 <现象>；做不到时写明需要谁在什么设备上确认>
- **完成标准**：<机器或肉眼可核对的完成条件>。
- **回滚**：<怎么撤回这次改动>。
````

## 写计划的人要注意

- 一个问题一份计划。两个问题共享所有文件和同一种修法（例如同一个缓动 token 替换涉及多个组件）时，可以合并成一份。
- 所有值都从对应镜头的参考文件里取（动效值从 [motion.md](motion.md) 第 4 节），不凭记忆估。
- 手感检查不能省。动效可能机械上正确但感觉不对；给执行者（或审查执行者 diff 的人）具体的慢放检查点。
- 写完计划后创建或更新 `plans/README.md`：计划表（编号、标题、级别、状态）、建议执行顺序、计划之间的依赖。
